# SEDWTIAR backend foundation

This service is a data-management foundation for IT assets, lifecycle events, and
sanitization evidence workflows. It deliberately contains no disk-wiping logic,
physical-device discovery, sanitization execution, AI/ML, or blockchain code.

## Local setup

1. Create a Python 3.11 virtual environment in `backend/.venv`.
2. Install `pip install -r requirements.txt`.
3. Copy `.env.example` to `.env` and supply PostgreSQL credentials.
4. Create the database schema through an approved migration process. Migration
   tooling is intentionally not introduced in this first foundation phase.
5. Run `uvicorn app.main:app --reload` from the `backend` directory.

## API scope

All application routes are under `/api/v1`.

- `GET /system/readiness` performs a harmless `SELECT 1` against PostgreSQL.
- `/assets` manages inventory metadata and lifecycle state.
- `/assets/{asset_id}/events` exposes append-only lifecycle events generated by
  the service layer.
- `/assets/{asset_id}/sanitization-records` stores administrative evidence only;
  adding a record never performs a sanitization operation.
- `/sanitization-jobs` records an administrative workflow only. Its state machine
  is `requested → prepared → evidence_recorded → verified`, with cancellation
  allowed before verification. A passed independent verification is required to
  transition a job to `verified`.
- `/sanitization-records/{record_id}/verifications` creates separate independent
  reviews. They are distinct from the legacy verification fields on a record.
- `/verifications/{verification_id}/certificate` issues immutable certificate
  metadata only after a passed review. The service derives a SHA-256 certificate
  hash and links each certificate to the preceding certificate hash when present;
  it does not perform signing, blockchain operations, or device actions.
- `/assets/{asset_id}/chain-of-custody` and
  `/assets/{asset_id}/disposition-recommendations` are create/read-only evidence
  records and recommendations, respectively.

Phase 2 adds tables to the Phase 1 schema. A migration framework remains out of
scope, so an approved schema-application process is required before using these
new PostgreSQL tables outside the in-memory test environment.

The tests use an in-memory SQLite database and do not connect to the configured
PostgreSQL instance or access physical storage.
